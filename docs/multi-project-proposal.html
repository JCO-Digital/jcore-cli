Running Multiple JCore Projects Concurrently

One shared Traefik proxy owns ports 80/443 and routes each request by hostname to the right project, so several https://<slug>.localhost sites (and their *.<slug>.localhost multisite subsites) can run side by side.

CLI-generated compose override

jcore start regenerates .jcore/compose.proxy.yml alongside .env, and adds COMPOSE_FILE="docker-compose.yml:.jcore/compose.proxy.yml" to .env. Compose reads that line itself, so every existing docker compose call in internal/docker — and plain docker compose run by hand — picks up the override with no code changes.

# .jcore/compose.proxy.yml — generated by jcore
services:
  web:
    ports: !reset []
    networks:
      jcore-proxy: {}
    labels:
      traefik.enable: "true"
      traefik.tcp.routers.acme.entrypoints: websecure
      traefik.tcp.routers.acme.rule: "HostSNI(`acme.localhost`)
        || HostSNIRegexp(`^.+\\.acme\\.localhost$$`)"
      traefik.tcp.routers.acme.tls.passthrough: "true"
      traefik.tcp.services.acme.loadbalancer.server.port: "443"
      fi.jco.jcore.project: acme
      fi.jco.jcore.domains: acme.localhost
      fi.jco.jcore.path: /home/me/projects/acme
  adminer:
    ports: !reset []
    networks: { default: {}, jcore-proxy: {} }
    labels:
      traefik.http.routers.acme-adminer.rule: Host(`adminer.acme.localhost`)
      # … port 8080, entrypoint web
  mailhog:
    # same pattern → mail.acme.localhost, port 8025
  loopback:
    image: alpine/socat:1.8.1.3
    network_mode: "service:wordpress"
    entrypoint: ["sh", "-c"]
    command: ["for p in 80 443; do (socat
      TCP6-LISTEN:$$p,fork,reuseaddr,ipv6only=0 TCP:web:$$p
      || socat TCP4-LISTEN:…) & done; wait"]
    restart: unless-stopped
networks:
  jcore-proxy: { external: true }
Requires Docker Compose ≥ 2.24

!reset was added in 2.24. jcore doctor gets a version check. The override only touches services the project's compose file defines; loopback is a complete service, added whenever the project has wordpress and web.

Multisite loopback: loopback sidecar

Changed during implementation

The agreed design was a CoreDNS sidecar plus a resolv.conf rewrite. Testing showed it can't work: curl, and so PHP's curl extension and the WordPress HTTP API, resolves every *.localhost name to 127.0.0.1 itself, without asking DNS (RFC 6761). For the same reason, the existing ${LOCAL_DOMAIN} network alias never worked for curl either, so wp-cron's loopback request never reached nginx.

Since curl always connects to 127.0.0.1 inside the wordpress container, the fix is to make the right thing listen there. A tiny alpine/socat service shares the wordpress container's network namespace (network_mode: service:wordpress) and forwards its 127.0.0.1:80/443 (and ::1) to web.

  • TLS isn't touched. curl still sends the original SNI and verifies web's *.acme.localhost cert.
  • Covers WP HTTP API, wp-cron, REST loopback, site health and wp-cli.
  • No image, entrypoint or sudo changes. Existing projects get it without jcore update.
  • Outbound traffic is unaffected.
Consequence: wp-cron now really runs locally

Production's auto_update_plugins option comes along with a database pull. During testing, balticsea auto-updated WooCommerce within a minute of starting. jcore now defines AUTOMATIC_UPDATER_DISABLED in .jcore/wordpress/wp-config.php before the containers start (and the entrypoint does for fresh installs). Other cron jobs, for example ones calling external APIs, will now run locally too.

Pitfalls the design avoids

Never attach wordpress, db or memcached to the shared network

Compose registers each service name as a DNS alias on every network the service joins. If two projects' wordpress containers sat on jcore-proxy, project A's nginx resolving fastcgi_pass wordpress:9000 could reach project B's PHP-FPM. Only web, adminer and mailhog join the shared network, and they only serve there. This is also why mail and Adminer stay per-project.

Don't change the compose project name

Volumes are named <dir>_db. Setting name: from the slug would silently orphan every existing database, so clashes are detected instead.

Tool hostnames vs multisite

adminer.<slug>.localhost and mail.<slug>.localhost are served over plain HTTP on :80. Over HTTPS the multisite wildcard passthrough sends them to WordPress, so those two subsite names are reserved.

Verified during implementation

  • All ten projects in ~/projects merge cleanly with the override (docker compose config), including customized compose files. fsl's own DB host port 5506 is left alone.
  • balticsea, carsam, prehealth and soilfood-multisite ran side by side. Every site, subsite, Adminer and mail URL routed correctly, with each project's own cert served through passthrough.
  • Each project's nginx resolves wordpress to its own container. No cross-project leakage.
  • wp_remote_get('https://se.soilfood.localhost/wp-json/') from inside WordPress returns 200 with certificate verification.
  • Traefik v3.7 accepts noop@internal. http:// site requests get redirected to https.
  • Same-name checkouts, domain clashes and ports held by an old-style project are all detected and explained.
  • Still open: Xdebug with start_with_request=yes. Several projects reaching one IDE listener on the same port attach to the same session unless their xdebugPorts differ.
