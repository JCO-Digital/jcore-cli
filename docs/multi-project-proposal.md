# Running Multiple Projects Concurrently

This document proposes how to let several JCore projects run at the same time,
each reachable on its existing `https://<slug>.localhost` domain (and
`*.<slug>.localhost` for multisite), by putting a single shared reverse proxy
in front of them.

## Decisions

| Topic | Decision |
| --- | --- |
| Proxy | Traefik v3, docker label discovery, TLS passthrough |
| Target platform | Linux + rootful Docker Engine |
| Domains | `*.localhost` only, so no DNS setup on the host |
| Proxy lifecycle | Auto-started by `jcore start`, `restart: unless-stopped`, stopped only by `jcore proxy stop` |
| `jcore stop` | Stops the current project. `--all` stops every project. Outside a project, shows a picker |
| `jcore start` | Still attached by default (unchanged) |
| Wiring existing projects | CLI-generated compose override (`.jcore/compose.proxy.yml`) via `COMPOSE_FILE` |
| Port conflicts / mixed CLI versions | Detect, explain, offer to stop the offender. No automatic legacy mode |
| Same-name checkouts | Detect and refuse |
| Adminer / mail | `http://adminer.<slug>.localhost`, `http://mail.<slug>.localhost` |
| MailHog | Swap image to Mailpit, keep the service name `mailhog` |
| Multisite loopback | Fix it: per-project `loopback` sidecar (socat) sharing the wordpress container's network namespace. *Changed during implementation, see §3* |
| WordPress auto-updates | Disabled locally (`AUTOMATIC_UPDATER_DISABLED`), since wp-cron now really runs. *Added during implementation, see §3* |
| Xdebug | `PHP_IDE_CONFIG=serverName=<slug>` always, plus a new `xdebugPort` setting (default 9003) |
| Resources | No CLI management. Developers use `status` / `stop` |
| Traefik dashboard | `http://traefik.localhost` |

## Why only one project can run today

| Blocker | Where |
| --- | --- |
| `web` publishes host ports `80` and `443` | `container/base/docker-compose.yml` |
| `adminer` publishes `1080`, `mailhog` publishes `1025` / `8025` | `container/base/docker-compose.yml` |
| `jcore start` refuses to start while another project runs (or stops it with `--force`) | `internal/cmd/run.go` (`startCmd`) |
| `jcore stop` stops *every* running project | `internal/cmd/run.go` (`stopCmd`) |

Everything else is already project-scoped: each compose project has its own
`default` and `jcore` networks, its own `db` volume, and its own TLS cert
(`.jcore/ssl/host.crt`, signed by the shared CA in `~/.config/jcore/ssl`).
`*.localhost` resolves to loopback on the host, so routing by hostname needs
no `/etc/hosts` changes.

So the job is mainly: **take the host ports away from the projects and give
them to one shared proxy that routes by hostname.**

## Target architecture

```text
                       host :80 / :443
                              │
                ┌─────────────▼──────────────┐
                │  jcore-proxy  (Traefik v3)  │   ~/.config/jcore/proxy/
                │  docker provider, labels    │   restart: unless-stopped
                └──────┬──────────────┬───────┘
          network: jcore-proxy (external, shared)
                       │              │
       ┌───────────────▼───┐   ┌──────▼────────────┐
       │ acme: web (nginx) │   │ foo: web (nginx)  │   only HTTP-facing
       │ adminer, mailhog  │   │ adminer, mailhog  │   services join the
       └───────┬───────────┘   └──────┬────────────┘   shared network
     acme_default network        foo_default network
       wordpress, db, memcached,   wordpress, db, memcached,
       loopback (socat)            loopback (socat)
```

### Traefik with TLS passthrough

The proxy routes on the **SNI hostname** and passes TLS straight through to
each project's own nginx (`tls.passthrough=true` on a TCP router). It never
decrypts anything.

- **No change to TLS.** Each project keeps its current cert, generated by the
  `tlscerts` container and signed by the already-trusted JCore CA.
  `site.conf` stays as it is.
- **Multisite works out of the box.** The rule
  `HostSNI(`acme.localhost`) || HostSNIRegexp(`^.+\.acme\.localhost$`)`
  matches the wildcard SAN the cert already has.
- **The CLI holds no proxy state.** A project is routable while its
  containers run. The CLI never edits or reloads proxy config.

## Changes

### 1. Shared proxy stack (`internal/proxy`, new)

The binary embeds a compose file and writes it to
`~/.config/jcore/proxy/docker-compose.yml`:

```yaml
name: jcore-proxy
services:
  traefik:
    image: traefik:v3
    restart: unless-stopped
    command:
      - --providers.docker=true
      - --providers.docker.exposedbydefault=false
      - --providers.docker.network=jcore-proxy
      - --entrypoints.web.address=:80
      - --entrypoints.websecure.address=:443
      - --api.dashboard=true
    ports: ["80:80", "443:443"]
    volumes: ["/var/run/docker.sock:/var/run/docker.sock:ro"]
    networks: [jcore-proxy]
    labels:
      traefik.enable: "true"
      traefik.http.routers.dashboard.rule: Host(`traefik.localhost`)
      traefik.http.routers.dashboard.entrypoints: web
      traefik.http.routers.dashboard.service: api@internal
      # Catch-all http -> https redirect, lowest priority so per-project
      # tool routers on :80 win.
      traefik.http.routers.to-https.rule: HostRegexp(`.+`)
      traefik.http.routers.to-https.priority: "1"
      traefik.http.routers.to-https.entrypoints: web
      traefik.http.routers.to-https.middlewares: to-https
      traefik.http.routers.to-https.service: noop@internal
      traefik.http.middlewares.to-https.redirectscheme.scheme: https
networks:
  jcore-proxy:
    external: true
```

- `proxy.Ensure()`:
  1. Creates the `jcore-proxy` network if it's missing. This also covers a
     `clean docker` network prune.
  2. Returns early if the proxy is already running.
  3. Checks that ports 80/443 are free. If a container holds them (typically
     a project started by an older CLI), it names that container and offers
     to stop it. If a host process holds them, it errors with a hint.
  4. Runs `docker compose up -d` on the stack.
- New commands: `jcore proxy start | stop | status | logs`.
- The proxy keeps running across project stops and reboots
  (`restart: unless-stopped`). Only `jcore proxy stop` takes it down. That
  avoids races between concurrent `start` / `stop` / Ctrl+C.

### 2. CLI-generated compose override

`jcore start` (and `GenerateEnvFile` callers such as `pull`) regenerate
`.jcore/compose.proxy.yml` alongside `.env`. Because it's an override, it
also works for projects with a customized `docker-compose.yml`:

```yaml
# Generated by jcore - do not edit.
services:
  web:
    ports: !reset []
    networks:
      jcore-proxy: {}
    labels:
      traefik.enable: "true"
      traefik.tcp.routers.acme.entrypoints: websecure
      traefik.tcp.routers.acme.rule: "HostSNI(`acme.localhost`) || HostSNIRegexp(`^.+\\.acme\\.localhost$$`)"
      traefik.tcp.routers.acme.tls.passthrough: "true"
      traefik.tcp.services.acme.loadbalancer.server.port: "443"
      fi.jco.jcore.project: acme
      fi.jco.jcore.domains: acme.localhost
      fi.jco.jcore.path: /home/me/projects/acme
  adminer:
    ports: !reset []
    networks: { default: {}, jcore-proxy: {} }
    labels:
      traefik.enable: "true"
      traefik.http.routers.acme-adminer.rule: Host(`adminer.acme.localhost`)
      traefik.http.routers.acme-adminer.entrypoints: web
      traefik.http.services.acme-adminer.loadbalancer.server.port: "8080"
  mailhog:
    ports: !reset []
    networks: { default: {}, jcore-proxy: {} }
    labels:
      traefik.enable: "true"
      traefik.http.routers.acme-mail.rule: Host(`mail.acme.localhost`)
      traefik.http.routers.acme-mail.entrypoints: web
      traefik.http.services.acme-mail.loadbalancer.server.port: "8025"
  loopback:
    image: alpine/socat:1.8.1.3
    network_mode: "service:wordpress"
    entrypoint: ["sh", "-c"]
    command: ["for p in 80 443; do (socat TCP6-LISTEN:$$p,fork,reuseaddr,ipv6only=0 TCP:web:$$p 2>/dev/null || socat TCP4-LISTEN:$$p,fork,reuseaddr TCP:web:$$p) & done; wait"]
    restart: unless-stopped
networks:
  jcore-proxy:
    external: true
```

`GenerateEnvFile` adds these lines to `.env`. Compose reads `COMPOSE_FILE`
on its own, and the wordpress container gets `PHP_IDE_CONFIG` through its
`env_file` (so a project's own `environment:` entry still wins):

```sh
COMPOSE_FILE="docker-compose.yml:.jcore/compose.proxy.yml"
PHP_IDE_CONFIG="serverName=acme.localhost"
```

**Every existing `docker compose` call in `internal/docker` picks up the
override with no change**, and so does a plain `docker compose` run by hand.

Notes:

- Rules come from the `domains` setting. Each domain `d` adds
  `HostSNI(d) || HostSNIRegexp(^.+\.d$)`. Values are written literally
  (no `${}` interpolation), and `$` is escaped as `$$`.
- Router names use the project slug.
- `!reset` requires **Docker Compose ≥ 2.24**. Add a `jcore doctor` check.
- The override only touches services the project's compose file defines.
  Otherwise compose would error on a service with no image. `loopback` is a
  complete service, added whenever the project has `wordpress` and `web`.

### 3. Multisite loopback: `loopback` sidecar

> **Changed during implementation.** The agreed design was a CoreDNS
> sidecar plus a `resolv.conf` rewrite. Testing showed that can't work:
> curl (and so PHP's curl extension and the WordPress HTTP API) resolves
> every `*.localhost` name to 127.0.0.1 itself, without asking DNS
> (RFC 6761). For the same reason, the existing `${LOCAL_DOMAIN}` network
> alias never worked for curl either, so wp-cron's loopback request never
> reached nginx.

Since curl always connects to 127.0.0.1 inside the wordpress container,
the fix is to make the right thing listen there. Each project gets a
`loopback` service (`alpine/socat`) that shares the wordpress container's
network namespace (`network_mode: service:wordpress`) and forwards its
127.0.0.1:80/443 (and `::1`) to `web`:

- TLS isn't touched. curl still sends the original SNI and verifies
  `web`'s certificate (`*.acme.localhost`, signed by the trusted JCore CA).
- It covers everything that goes through curl, which is the WP HTTP API,
  wp-cron, REST loopback, site health and wp-cli.
- There are no image, entrypoint or sudo changes. The override adds it, so
  existing projects get it without `jcore update`.
- Outbound traffic is unaffected. Only connections to the container's own
  loopback are forwarded.

Verified on `soilfood-multisite` (subdomain multisite): from inside its
wordpress container, `wp_remote_get('https://se.soilfood.localhost/wp-json/')`
returns 200 with certificate verification.

**Consequence: wp-cron now really runs locally.** That's correct
WordPress behaviour (scheduled posts, Action Scheduler and so on), but
production's `auto_update_plugins` option comes along with a database
pull. During testing, `balticsea` auto-updated WooCommerce within a minute
of starting. So jcore now defines `AUTOMATIC_UPDATER_DISABLED` in
`.jcore/wordpress/wp-config.php` on the host before the containers start,
and `docker-entrypoint.sh` sets it for fresh installs. Other cron jobs, for
example ones calling external APIs, will now run locally too.

### 4. Command semantics

| Command | Today | Proposed |
| --- | --- | --- |
| `start` | Refuses if any project runs; `--force` stops them | Runs `proxy.Ensure()`, the name-clash check and the domain-clash check, then starts *this* project. Attached by default as today. `--force` is removed (or kept as a no-op with a deprecation notice) |
| `stop` | Stops all projects | Stops the **current** project. `--all` stops every project (the proxy keeps running). Outside a project with no flag, shows the TUI picker |
| `status` | "Project X is running" | Table of project / domains / state / path from `fi.jco.jcore.*` labels, plus proxy state and the adminer/mail URLs |
| `proxy` | — | `start`, `stop`, `status`, `logs` |
| `doctor` | — | Checks: Compose ≥ 2.24, :80/:443 held by something other than `jcore-proxy`, proxy running |

Clash checks in `start`:

- **Same compose project name, different path.** `docker compose ls -a`
  reports a project with the same name whose config file lives elsewhere.
  Refuse and explain that two checkouts share a directory name, and so would
  share containers and the DB volume. The compose project name stays the
  directory name, so existing volumes are never orphaned.
- **Domain clash.** A *running* `web` container from another project has
  an `fi.jco.jcore.domains` label that overlaps this project's `domains`.
  Refuse and name the other project.

The labels also replace the `docker compose ls` + "does `.jcore/` exist"
heuristic in `ListDockerProjects`.

### 5. Base compose and template changes

- `container/base/docker-compose.yml`: remove the host `ports` from `web`,
  `adminer` and `mailhog`. Change `mailhog`'s image to `axllent/mailpit`,
  keeping the service name `mailhog` so the WordPress image's SMTP host keeps
  working. New and updated projects are then clean even without the override.
- `container/base/.config/docker-entrypoint.sh`: sets `AUTOMATIC_UPDATER_DISABLED` for fresh installs.
- `container/base/php.ini`: add `xdebug.client_port={{.XdebugPort}}`. Add
  `XdebugPort` to `TemplateData` and `xdebugPort` to the config schema
  (default 9003).
- `container/base/readme.md`: new URLs (`adminer.<slug>.localhost`,
  `mail.<slug>.localhost`, `traefik.localhost`).

## Pitfalls this design deliberately avoids

- **Never attach `wordpress`, `db` or `memcached` to the shared
  network.** Compose registers each service name as a DNS alias on every
  network the service joins. If two projects' `wordpress` containers both sat
  on `jcore-proxy`, project A's nginx resolving `fastcgi_pass wordpress:9000`
  could reach project B's PHP-FPM. Only `web`, `adminer` and `mailhog` join
  the shared network, and they only *serve* there. This is also why mail and
  Adminer stay per-project.
- **Don't change the compose project name.** Volumes are named
  `<project>_db` after the directory, so renaming would silently orphan
  databases. Clashes are detected instead.
- **Tool hostnames vs multisite.** `adminer.<slug>.localhost` and
  `mail.<slug>.localhost` are served over plain HTTP on :80. Over HTTPS, the
  multisite wildcard passthrough sends them to WordPress. This reserves those
  two subsite names.

## Verified during implementation

- **CoreDNS** wasn't viable (see §3) and was replaced by the `loopback`
  sidecar.
- **`noop@internal`** works as the redirect router's service on Traefik
  v3.7: `http://` site requests get a 302 to https.
- **Overrides on real projects.** `docker compose config` merges cleanly for
  all ten projects in `~/projects`, including the customized
  `fsl` / `kadenjalki2022` / `soilfood-multisite` compose files. `fsl`'s
  own DB host port (5506) is left alone.
- **Concurrency.** `balticsea`, `carsam`, `prehealth` and
  `soilfood-multisite` ran side by side. Each site, subsite, Adminer and
  mail URL routed correctly, and each project's nginx resolves `wordpress`
  to its own container.
- **Still open: Xdebug with `start_with_request=yes`.** Every project
  tries to reach the host on its `xdebugPort`. With several projects
  running and one IDE listening, requests from the others attach to the
  same session unless their ports differ.

## Suggested rollout

1. `internal/proxy`: embedded stack, `Ensure()` with port-conflict detection,
   `jcore proxy …` commands.
2. Override generation (incl. `loopback`), `COMPOSE_FILE` in `.env`, base
   compose changes (ports, Mailpit), disabling WordPress auto-updates.
3. `start` / `stop` / `status` / `doctor` semantics, clash checks,
   label-based project listing.
4. `xdebugPort` setting + `PHP_IDE_CONFIG`.
5. Docs: `docs/commands.md`, `docs/configuration.md`, CHANGELOG. The change
   to `stop` and the new tool URLs need callouts.
